# Navigation and layouts

## Route identity

- `apps/frontend/src/lib/app-surfaces.ts` declares every surface (anything with a route and an identity: title, label, description, icon, nav placement) once. A parent surface nests its children inline; `id`/`parentId` are derived. No surface declares `nav` today: the app's navigation is the documentation sidebar, which comes from the content (`v1.docs.nav`), not from the registry.
- `apps/frontend/src/lib/site-nav.ts` is projected from it: `adminSidebarLinks` (the admin shell's rows, from the `admin` surface's children), `siteNavItems` (for `SectionNavOverview`) and the search groups. Never hardcode a label, icon or description in a sidebar, menu or overview component.
- The navbar surface search (`⌘K`/`Ctrl+K`, `features/app-shell/authenticated/components/surface-search-dialog.tsx`) lists `getSearchableSurfaces(isAdmin)` from `site-nav.ts`: every surface with a concrete path, minus `adminOnly` ones for non-admins. A new surface is searchable automatically; set `search: false` on surfaces that are not a destination for a signed-in user (login, signup, 404). Dynamic `[param]` routes are never listed as surfaces; one becomes reachable through its records by declaring `searchSource` (a `SurfaceSearchSourceId` key in `app-surfaces.ts`) with a matching entry in `features/app-shell/authenticated/model/surface-search-sources.ts`. A source always calls its own entity's procedure. A record may bring its own `href` and `trail` instead of path params (the documentation pages source does: its pages are a tree under `/[repo]/[...path]`, read from `v1.docs.nav`, the sidebar's own query, so the search costs no request). An entity listed in full uses `defineSearchSource` with a Spanish group heading plus the list page's own `orpc.v1.<feature>.list.queryOptions()` and a `select` that maps each record to its path params, label and description (same query key, so the search shares the list's cache and invalidation); its records load once while the dialog is open. An entity listed in pages uses `defineServerSearchSource` with its own `orpc.v1.<feature>.search.queryOptions({ ...serverSearchQuery(options), select })`, a `search` procedure written per `references/api/free-text-search.md` (the registry's doc comment has a full entry). `useSurfaceSearchRecords` asks it for the text 150 ms after the last keystroke, minus the words its own section labels already contain ("dispositivos lectura" asks for "lectura"), only with 2 characters or more, for 5 records, and keeps the previous answer while the next loads. A record whose endpoint matched a term its label doesn't show (an address, a code) lists it in the entry's `keywords` so the dialog's filter keeps it. Records show only once the user types. The dialog matches every word of the query separately: each word must appear in the result's label, description, group, trail or keywords, so "admin cuentas" finds Usuarios and "red dns" finds that page. Records also match on the labels of their surface and of the concrete-path surfaces above their route, so typing a section's name lists its records. The match score stays binary, so results keep their registry order and a server source's order. Every sub-page and record shows its section trail before its label (`Admin › Usuarios`, `Red › DNS`): `trail` on `SiteNavSearchItem`, rendered by the slice's `SurfaceSearchLabel`. Exact visits to concrete-path surfaces are recorded per user in `localStorage` (`lib/recent-surfaces.ts`) and shown as a "Recientes" group while the query is empty; record pages are never recents.
- Icons are resolved through `apps/frontend/src/lib/icon-registry.ts`.
- Active-route matching goes through `isNavLinkActive(href, pathname)`, never a bare `startsWith`. The documentation sidebar marks only the row whose `href` equals the current path.

## Navbar and admin entry

- `NavbarAuthenticated` (`features/app-shell/authenticated`) shows the brand, the surface search, the theme menu and the user menu; it renders no section links. On pages whose `<body>` carries `data-docs-sidebar` (set by `Docs.astro`) it adds, below `md`, a menu button that dispatches `docs-sidebar:toggle` (`features/docs/shared/model/sidebar-toggle.ts`); the sidebar island listens and opens its sheet. The two islands share nothing else.
- Admin is not a navigation section: `UserNav` offers "Administración" (`/admin`) to admins, and the admin shell's footer links back to `/`.

## Layouts (`apps/frontend/src/layouts/`)

- `Layout.astro` — the default: navbar (guest or authenticated) + slot + footer. Props include `guestNavbar`, `hideFooter` (also locks the body to the viewport, for login/signup), `footer={false}` (no footer, window still scrolls), `animateContent` and `scrollToTop`. Used by `/me`, login, signup and 404.
- `Docs.astro` — the documentation reader (`/`, `/<slug>`, `/<slug>/<path>`): `Layout` without footer and with `animateContent={false}`, a sticky `DocsSidebar` island (`features/docs/sidebar`, `transition:persist="docs-sidebar"`, its wrapper reserves the column's width before hydration) and the page column, which alone fades. Takes `title`, `nav` (the `v1.docs.nav` answer, the sidebar's `initialData`), `storedScope` (the `docs_scope` cookie) and `wide`; an `aside` slot holds the table of contents. The window scrolls, so anchors, the TOC and the browser's own scroll restoration work as on any page. The page content is Astro rendered on the server (`features/docs/page`), read through the server oRPC client (`references/frontend/data-fetching.md`).
  - The repository selector writes the `docs_scope` cookie (`todos` or a slug) and navigates; the page route moves it to the page's repository unless it says `todos` (`scopeToStore`), and `/` redirects to the remembered repository. With one repository the scope is that one and nothing is stored (`features/docs/shared/model/scope.ts`).
  - The sidebar keeps its open sections and scroll in the persisted island, and in `sessionStorage` (`docs-sidebar`) across reloads; it scrolls the current row into view only when it is out of sight.
- `Admin.astro` — the `/admin` section with its `AdminShell` sidebar (`features/admin/shell`); gated by `role === "admin"` in `src/middleware.ts`. Takes `scrollToTop`. `AdminShell` already pads the page and fills the viewport's height, so every admin page uses all of the inset: `PageShell` (or `ResourceOverview`) with `maxWidth="full"` and `padding="none"`.
- `Detail.astro` — a detail route outside the admin shell and the reader. Takes `title`, `backHref`, `backLabel`, `maxWidth` and `scrollToTop` (passed through to `Layout`) and renders `<main>` plus the back link itself, so the mounted island must not wrap itself in `PageShell` (that would nest a second `<main>`): wrap it in `QueryProvider` and render `PageHero` directly. No route uses it today.
- Scroll-to-top: `Layout.astro` and `Admin.astro` each mount `ScrollToTopButton` (`components/shared/layout/scroll-to-top-button.tsx`) once inside `.scroll-to-top-root` (`styles/global.css`). It only shows on pages that opt in — `scrollToTop` on `Layout`, `Docs`, `Admin` or `Detail` stamps `data-scroll-to-top` on the swapped content. On mobile it rises above the filter action bar through `--list-action-bar-offset`.
- Pick the layout by navigation context; a route renders exactly one `<main>`.

Navigation chrome lives in `features/app-shell/` (`authenticated`, `guest`), `features/docs/sidebar` and `features/admin/shell`; `components/shared` never renders chrome.
