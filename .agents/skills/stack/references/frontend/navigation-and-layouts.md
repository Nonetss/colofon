# Navigation and layouts

## Route identity

- `apps/frontend/src/lib/app-surfaces.ts` declares every surface (anything with a route and an identity: title, label, description, icon, nav placement) once. A parent surface nests its children inline; `id`/`parentId` are derived. Only surfaces with `nav` appear in navbar/sidebar navigation.
- `apps/frontend/src/lib/site-nav.ts` is projected from it (`siteNavItems`, `subItems`, `getSidebarSection`, …). Never hardcode a label, icon or description in a navbar, sidebar or overview component.
- The navbar surface search (`⌘K`/`Ctrl+K`, `features/app-shell/authenticated/components/surface-search-dialog.tsx`) lists `getSearchableSurfaces(isAdmin)` from `site-nav.ts`: every surface with a concrete path, minus `adminOnly` ones for non-admins. A new surface is searchable automatically; set `search: false` on surfaces that are not a destination for a signed-in user (login, signup, 404). Dynamic `[param]` routes are never listed as surfaces; one becomes reachable through its records by declaring `searchSource` (a `SurfaceSearchSourceId` key in `app-surfaces.ts`) with a matching entry in `features/app-shell/authenticated/model/surface-search-sources.ts`. A source always calls its own entity's procedure. An entity listed in full uses `defineSearchSource` with a Spanish group heading plus the list page's own `orpc.v1.<feature>.list.queryOptions()` and a `select` that maps each record to its path params, label and description (same query key, so the search shares the list's cache and invalidation); its records load once while the dialog is open. An entity listed in pages uses `defineServerSearchSource` with its own `orpc.v1.<feature>.search.queryOptions({ ...serverSearchQuery(options), select })`, a `search` procedure written per `references/api/free-text-search.md` (the registry's doc comment has a full entry). `useSurfaceSearchRecords` asks it for the text 150 ms after the last keystroke, minus the words its own section labels already contain ("crons limpieza" asks for "limpieza"), only with 2 characters or more, for 5 records, and keeps the previous answer while the next loads. A record whose endpoint matched a term its label doesn't show (an address, a code) lists it in the entry's `keywords` so the dialog's filter keeps it. Records show only once the user types. The dialog matches every word of the query separately: each word must appear in the result's label, description, group, trail or keywords, so "configuracion tema" finds Apariencia and "crons limpieza" finds that job. Records also match on the labels of their surface and of the concrete-path surfaces above their route, so typing "crons" lists every cron job. The match score stays binary, so results keep their registry order and a server source's order. Every sub-page and record shows its section trail before its label (`Configuración › Apariencia`, `Crons › <job>`): `trail` on `SiteNavSearchItem`, rendered by the slice's `SurfaceSearchLabel`. Exact visits to concrete-path surfaces are recorded per user in `localStorage` (`lib/recent-surfaces.ts`) and shown as a "Recientes" group while the query is empty; record pages are never recents.
- Icons are resolved through `apps/frontend/src/lib/icon-registry.ts`.
- Active-route matching goes through `isNavLinkActive(href, pathname)`, never a bare `startsWith`.

## Layouts (`apps/frontend/src/layouts/`)

- `Layout.astro` — the default: navbar (guest or authenticated) + slot + footer. Props include `guestNavbar`, `hideFooter`, `scrollToTop`.
- `Admin.astro` — the `/admin` section with its `AdminShell` sidebar (`features/admin/shell`); gated by `role === "admin"` in `src/middleware.ts`. Takes `scrollToTop`. `AdminShell` already pads the page and fills the viewport's height, so every admin page uses all of the inset: `PageShell` (or `ResourceOverview`) with `maxWidth="full"` and `padding="none"`.
- `WithSidebar.astro` — a section with sub-surfaces. Takes `section` (the section href, must declare `subItems`), plus `persistScroll` and `scrollToTop`. Reads the `sidebar_state` cookie server-side so the sidebar doesn't flash open.
  - The page scrolls inside `<main data-app-scroller>`, not the window, so Astro's own scroll restoration never applies. The persisted `WithSidebarHeader` island (`features/app-shell/sidebar`) restores that offset per path plus query string through `useElementScrollRestoration` (`hooks/use-scroll-restoration.ts`), synchronously on `astro:after-swap`.
  - The saved state includes the content height. On return it is reserved as `min-height` on the `data-app-scroll-content` wrapper, so the offset applies before the `client:only` islands render. The reservation goes when the content reaches it, on a pointer or key press in the scroller, on the next swap, or after `RESERVE_MS`. Never put the reservation on the scroller itself, and never wait for content with retries.
  - `persistScroll` is `true` by default (save and restore); `false` starts at the top and saves nothing, for pages that should always open at their top.
- Scroll-to-top: `Layout.astro` and `Admin.astro` each mount `ScrollToTopButton` (`components/shared/layout/scroll-to-top-button.tsx`) once inside `.scroll-to-top-root` (`styles/global.css`). It only shows on pages that opt in — `scrollToTop` on `Layout`, `Admin`, `WithSidebar` or `Detail` stamps `data-scroll-to-top` on the swapped content (the app scroller in `WithSidebar`). On mobile it rises above the filter action bar through `--list-action-bar-offset`.
- `Detail.astro` — detail routes whose parent is not a sidebar section (e.g. `/crons/[id]`). Takes `title`, `backHref`, `backLabel`, `maxWidth` and `scrollToTop` (passed through to `Layout`) and renders `<main>` plus the back link itself, so the mounted island must not wrap itself in `PageShell` (that would nest a second `<main>`): wrap it in `QueryProvider` and render `PageHero` directly. Reference: `features/crons/detail/components/cron-detail-{page,content}.tsx`.
- Detail routes under a sidebar section use `WithSidebar.astro` with that section instead. Pick the layout by navigation context; a route renders exactly one `<main>`.

Navigation chrome lives in `features/app-shell/` (`authenticated`, `guest`, `sidebar`) and `features/admin/shell`; `components/shared` never renders chrome.
