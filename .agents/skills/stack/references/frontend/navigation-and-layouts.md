# Navigation and layouts

## Route identity

- `apps/frontend/src/lib/app-surfaces.ts` declares every surface (anything with a route and an identity: title, label, description, icon, nav placement) once. A parent surface nests its children inline; `id`/`parentId` are derived. No surface declares `nav` today: the app's navigation is the documentation sidebar, which comes from the content (`v1.docs.nav`), not from the registry.
- `apps/frontend/src/lib/site-nav.ts` is projected from it: `sectionSidebarLinks(id, overviewLabel)` (a section's sidebar rows: its own page under `overviewLabel`, then its child surfaces in registry order), with `adminSidebarLinks` (the admin shell, "Resumen") and `sectionSidebars` (the sections `WithSidebar.astro` shows, today `profile` with "Cuenta") built on it, `currentNavHref(pathname, hrefs)` (the one current row of a section: the most specific match), `siteNavItems` (for `SectionNavOverview`) and the search groups. Never hardcode a label, icon or description in a sidebar, menu or overview component.
- The navbar search (`⌘K`/`Ctrl+K`, `features/app-shell/authenticated/components/surface-search-dialog.tsx`) lists only the pages of the content repositories, from the `doc-pages` source, and the catalog entities `v1.docs.search` returns. It does not list the app's surfaces (home, profile, admin). `getSearchableSurfaces(isAdmin)` in `site-nav.ts` still projects every concrete-path surface the user may see (no dynamic `[param]` routes, no `search: false`, `adminOnly` only for admins); the palette does not render that list. Set `search: false` on a concrete surface that is not a destination for a signed-in user (login, signup, 404). Dynamic `[param]` routes are never listed as surfaces; one becomes reachable through its records by declaring `searchSource` (a `SurfaceSearchSourceId` key in `app-surfaces.ts`) with a matching entry in `features/app-shell/authenticated/model/surface-search-sources.ts`. A source always calls its own entity's procedure. A record may bring its own `href` and `trail` instead of path params (the documentation pages source does: its results come from `v1.docs.search` with their route, section anchor included). An entity listed in full uses `defineSearchSource` with a Spanish group heading plus the list page's own `orpc.v1.<feature>.list.queryOptions()` and a `select` that maps each record to its path params, label and description (same query key, so the search shares the list's cache and invalidation); its records load once while the dialog is open. An entity listed in pages uses `defineServerSearchSource` with its own `orpc.v1.<feature>.search.queryOptions({ ...serverSearchQuery(options), select })`, a `search` procedure written per `references/api/free-text-search.md` (the registry's doc comment has a full entry). The dialog debounces the text (150 ms after the last keystroke) and `useSurfaceSearchRecords` asks the source for it, minus the words its own section labels already contain ("dispositivos lectura" asks for "lectura"), only with 2 characters or more, for 5 records, and keeps the previous answer while the next loads. A record whose endpoint matched a term its label doesn't show (an address, a code) lists it in the entry's `keywords` so the dialog's filter keeps it. Records show only once the user types. The dialog matches every word of the query separately: each word must appear in the result's label, description, group, trail or keywords, so "red dns" finds that page. Records also match on the labels of their surface and of the concrete-path surfaces above their route, so typing a section's name lists its records. The match score stays binary, so results keep their registry order and a server source's order. Every page shows its section trail before its label (`Red › DNS`): `trail` on `SiteNavSearchItem`, rendered by the slice's `SurfaceSearchLabel`. Sources get the dialog's `scope` (the repository it searches, `undefined` for every one): the dialog starts from the `docs_scope` cookie each time it opens and offers a two-option switch inside the input row (`SurfaceSearchScope`, dressed like `SegmentedPicker`) between that repository and "Todos" for this search only (Tab or Shift+Tab in the input toggles it, keeping the focus there, and the footer legend shows `tab` only then), never writing the cookie (`model/search-scope.ts`). The partial flag and the entities aren't records of a surface: `useDocsSearchMeta` spreads the same `docsSearchQuery` input as the `doc-pages` source with another `select`, so both read one cached request; the "Catálogo" group goes before the pages when an entity is `exact`. A record's other matching `sections` render as indented items with the page's keywords, and its `missing` words struck through. With an empty query the dialog lists "Recientes": the navbar records each documentation page the user opens (`recordableDocPath`, no entity pages or app screens) in `lib/recent-surfaces.ts`'s per-user list `doc-pages`, and the dialog resolves them against `v1.docs.nav`, dropping what no longer resolves. Selecting a result while typing stores the searched words for that address (`lib/search-highlight.ts`, one-shot `sessionStorage`); the documentation page's `page-scripts.ts` takes them on load and marks them in the target section with the CSS Custom Highlight API (`::highlight(search-match)` in `styles/doc/page.css`).
- Icons are resolved through `apps/frontend/src/lib/icon-registry.ts`.
- Active-route matching goes through `isNavLinkActive(href, pathname)`, never a bare `startsWith`. The documentation sidebar marks one row, `currentHref(nodes, pathname)` (`features/docs/shared/model/nav.ts`): the page itself when the navigation lists it, otherwise the deepest listed page above it by path (an entity page marks its catalog type), and opens the sections that hold that row.

## Navbar and admin entry

- `NavbarAuthenticated` (`features/app-shell/authenticated`) shows the brand, the surface search, the theme menu and the user menu; it renders no section links. On pages whose `<body>` carries `data-page-sidebar` with the sidebar's element id (set by `Docs.astro` and `WithSidebar.astro`) it adds, below `md`, a menu button (`aria-controls` that id) that dispatches `page-sidebar:toggle` (`src/lib/page-sidebar.ts`, read through `usePageSidebarId` in `src/hooks/use-page-sidebar.ts`); the page's sidebar island listens, opens its sheet and closes it after navigating. The islands share nothing else.
- Admin is not a navigation section: `UserNav` offers "Administración" (`/admin`) to admins, and the admin shell's footer links back to `/`.

## Layouts (`apps/frontend/src/layouts/`)

- `Layout.astro` — the default: navbar (guest or authenticated) + slot + footer. A named `head` slot adds tags to `<head>`. Props include `guestNavbar`, `hideFooter` (also locks the body to the viewport, for login/signup), `footer={false}` (no footer, window still scrolls), `animateContent` and `scrollToTop`. Used by login, signup and 404.
- `WithSidebar.astro` — a section with sub-pages outside `/admin` (today the profile: `/me`, `/me/api-keys`, `/me/secrets`, `/me/repositories`, `/me/organizations`, `/me/skills`): `Layout` without footer and with `animateContent={false}`, the section's sidebar (`SectionSidebarChrome`, `features/app-shell/sidebar`, `transition:persist="section-sidebar-<section>"`) and the page column, which fades on navigation. Takes `title`, `section` (a key of `sectionSidebars`) and `scrollToTop`; redirects to `/login` without a user. The window scrolls; the shadcn sidebar (`collapsible="icon"`, state in the `sidebar_state` cookie it shares with the admin shell) is fixed below the navbar and its gap reserves the column, and below `md` it is a sheet the navbar's menu button opens. Its rows come only from `sectionSidebars`, so a new page in a section is a child surface in `app-surfaces.ts` plus its route; to give another section this layout, add it to `sectionSidebars`. Pages mount a `*-page.tsx` with `PageShell` (the layout renders no `<main>`); sub-pages head with `PageHero surface="…"`.
- `Docs.astro` — the documentation reader (`/`, `/<slug>`, `/<slug>/<path>`): `Layout` without footer and with `animateContent={false}`, a sticky `DocsSidebar` island (`features/docs/sidebar`, `transition:persist="docs-sidebar"`, its wrapper reserves the column's width before hydration) and the page column, which alone moves (a short rise and fade, `page-enter` in `styles/app/chrome.css`). It also mounts `DocLightbox` once (`features/docs/lightbox`, `transition:persist="docs-lightbox"`), the viewer that opens the page's images, and a copy of a diagram's drawing (from the "Ampliar" button `renderBlocks` adds to each drawn diagram; the drawing itself never opens the viewer, so its boxes, arrows and links keep the pointer), enlarged with zoom and drag. The stage only captures the pointer once a press becomes a drag, and the viewer closes when a link inside it navigates. A diagram's hover highlighting and card (`features/docs/diagrams`: `model/diagram-highlights.ts`, on the pure `diagram-graph.ts`) is set up once by `onDocsPageLoad` (`features/docs/page/model/page-scripts.ts`), listens on the document and works on the lightbox's copy too. Takes `title`, `nav` (the `v1.docs.nav` answer, the sidebar's `initialData`), `storedScope` (the `docs_scope` cookie) and `wide`; an `aside` slot holds the table of contents and a `head` slot is forwarded to `Layout` (a page announces its Markdown with `<link rel="alternate" type="text/markdown">` there). The window scrolls, so anchors, the TOC and the browser's own scroll restoration work as on any page. The page content is Astro rendered on the server (`features/docs/page`), read through the server oRPC client (`references/frontend/data-fetching.md`).
  - The page body (`DocBody`) is `renderBlocks` (`features/docs/page/model/render.ts`) over the API's tree: code and table frames (a fence is coloured with TanStack Highlight, `model/code-highlight.ts`: the fence language becomes `th-*` spans inside the `<code>`, from the `--th-*` palette; `mdx` as Markdown and a leading `---` block as YAML), key/value tables (an empty first header cell), zoomable images, and the repeated sections known by their `##` heading (`model/sections.ts`, icons in the registry's `docSections` group) split out so `DocBody` wraps each in a `.doc-section` with its icon. In the browser, the `DocTables` island (`features/docs/tables`, `components/doc-tables.tsx`, mounted by `doc-body.astro`) makes every table except key/value ones interactive over the server's HTML: `model/table-dom.ts` turns each header into a sort button, adds slots and the toolbar/pager containers, and applies each view by moving, hiding and marking the server's `tr`s. The controls are React through portals: `DocTableToolbar` (box with `column:value`, count, columns menu, copy as Markdown, CSV, link to the view, full screen), the shared `DataTableColumnFilter` right after the name of each header whose values fit the panel (a column of long text has none), chips, `FilteredEmpty` and `DocTablePager`. Each table is a TanStack table (`hooks/use-doc-table.ts`: `useTable` from `@tanstack/react-table` with `table-core`'s sorting, column and global filtering, faceting, pagination and visibility features, state controlled in TanStack's shapes); its columns, global filter, chips and facet options are in `model/doc-table.ts`, with type-aware sort keys from `table-kinds.ts`, the `column:value` box from `table-query.ts`, the table read from the DOM and its labels in `table-view.ts` (toolbar from 2 rows, pages of 25 above 50), the view in the URL with the earlier site's keys (`table-url.ts`) and the exports (`table-export.ts`). Page tables fit the reading column and wrap their cells (`styles/doc/tables.css` overrides the typeset's `max-content` width). A handle on each header's trailing edge resizes that column (`model/table-resize.ts`: drag, arrow keys in 16 px steps, double-click restores automatic widths); dragging an edge gives the space to the next column, so the table keeps its width; the last visible column has no handle, since its edge is the table's. Never give a page table a vanilla control or a `title`: add it to the island. Sections and the "Todos" home show their children as `DocCard`s (`features/docs/shared`), split by `cardBlocks()` into one block per group of the repository's `menu.yaml`, headed by its title. Catalog pages (`catalog/…`) are ordinary pages to the reader: the backend generates them. A breadcrumb with a `null` href is a menu group, shown as text.
  - A repository's own styles (`content-styles`, its optional `styles/<módulo>.css`, one per platform module) come cleaned by the backend in `v1.docs.page`'s `styles`; `[repo]/[...path].astro` passes them to `Docs.astro`, which inlines them as an unlayered `<style is:inline>` after the page content, inside the swapped body: after the platform's stylesheet (so they win where both meet, tokens included) and gone when the reader leaves for another repository, the "Todos" home or `/admin`. Never add a platform class or variable a repository may style without documenting it in `doc-example/docs/repository/styles.mdx`, and treat renaming one as a contract change.
  - The page body's look lives in `src/styles/doc/`, one plain-CSS module per piece of the page (`page`, `hints`, `code`, `tables`, `diagrams`, `images`, `callouts`, `sections`), imported by `global.css` in that order: a later module overrides an earlier one where their rules meet, so keep the order when adding one. The modules use only plain CSS and the theme's variables (no `@apply` or other Tailwind directives), and every selector starts at `.typeset.doc` (outside the page body, the lightbox and the diagram card use their own `.doc-lightbox*` and `.doc-diagram-tip*` classes). `global.css` itself is only the Tailwind entry: it imports the vendored `typeset.css`, then `src/styles/theme.css` (the theme tokens: `:root`, `.dark` and `@theme inline`; it is the file `components.json` points shadcn at, so an added component's variables land there), then the app-wide modules of `src/styles/app/` (`typeset-presets`, `syntax`, `base`, `chrome`, `utilities`, `charts`) and then these.
  - The repository selector writes the `docs_scope` cookie (`todos` or a slug) and navigates; the page route moves it to the page's repository unless it says `todos` (`scopeToStore`), and `/` redirects to the remembered repository. With one repository the scope is that one and nothing is stored (`features/docs/shared/model/scope.ts`).
  - The table of contents column (`DocToc`) also holds "Copiar en Markdown" (the page written back from its tree by `pageMarkdown`, `packages/api/src/v1/docs/markdown.ts`, embedded as JSON and copied with full URLs) and "Ancho completo", which toggles `data-reading-width-full` on `<html>` (stored as `docs-width`, reapplied before painting by `Layout.astro`); styles follow it with the `reading-full:` variant. `withOrigin` (`packages/api/src/v1/docs/full-links.ts`, imported alone by the copy script so the Markdown writer stays out of the browser) makes those URLs full for the copy and for `llm.txt`.
  - Beside the reader, Markdown routes for AIs (`features/docs/llm-text`): `/llms.txt` (every repository, per llmstxt.org) and `/<slug>/llms.txt` (one repository) list each page as a link to its `<page>/llm.txt`, the same text "Copiar en Markdown" copies. The texts are built in `packages/api/src/v1/docs/` (`llm-text.ts`, `markdown.ts`), which the MCP's `index` and `read` tools also use (`references/api/mcp.md`), so the routes and the MCP always answer the same. They answer `text/plain`, read with a session or an `x-api-key`, and without one get a 401 instead of the login redirect (`references/env.md`).
  - `v1.docs.nav` nodes are `page`, `section` or `group` (a heading of `menu.yaml`, no route, top level only). `DocsNavTree` renders a group as a label with its icon over its own rows; `shared/model/nav.ts` passes through groups for the search trail (`Infraestructura › Red › DNS`), the open sections and the page counts.
  - The sidebar keeps its open sections and scroll in the persisted island, and in `sessionStorage` (`docs-sidebar`) across reloads; it scrolls the current row into view only when it is out of sight.
- `Admin.astro` — the `/admin` section with its `AdminShell` sidebar (`features/admin/shell`); gated by `role === "admin"` in `src/middleware.ts`. Takes `scrollToTop`. `AdminShell` already pads the page and fills the viewport's height, so every admin page uses all of the inset: `PageShell` (or `ResourceOverview`) with `maxWidth="full"` and `padding="none"`.
- `Detail.astro` — a detail route outside the admin shell and the reader. Takes `title`, `backHref`, `backLabel`, `maxWidth` and `scrollToTop` (passed through to `Layout`) and renders `<main>` plus the back link itself, so the mounted island must not wrap itself in `PageShell` (that would nest a second `<main>`): wrap it in `QueryProvider` and render `PageHero` directly. No route uses it today.
- Scroll-to-top: `Layout.astro` and `Admin.astro` each mount `ScrollToTopButton` (`components/shared/layout/scroll-to-top-button.tsx`) once inside `.scroll-to-top-root` (`styles/app/chrome.css`). It only shows on pages that opt in — `scrollToTop` on `Layout`, `Docs`, `WithSidebar`, `Admin` or `Detail` stamps `data-scroll-to-top` on the swapped content. On mobile it rises above the filter action bar through `--list-action-bar-offset`.
- Pick the layout by navigation context; a route renders exactly one `<main>`.

Navigation chrome lives in `features/app-shell/` (`authenticated`, `guest`, `sidebar`), `features/docs/sidebar` and `features/admin/shell`; `components/shared` never renders chrome.
