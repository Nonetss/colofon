# Entity icons (user-chosen Lucide icon + color)

A polymorphic building block, like comments: any entity can carry one Lucide icon and one palette color, chosen by the user. No entity type is registered yet: `entityIconTargets` is empty, so every call is `BAD_REQUEST` until the first consumer opts in.

## Pieces

- **Table** `entity_icons` (`packages/db/src/schema/entity-icon/`): `(entity_type, entity_id)` unique, `icon` (kebab-case Lucide name), `color` (palette key, `entityIconColors`). No foreign key to targets.
- **API** `orpc.v1.entityIcon.{getMany,set,clear}` (`packages/api/src/v1/entity-icon/`). Every call goes through the registry in `targets.ts`; an unregistered `entityType` is `BAD_REQUEST`, a target the caller may not modify is `NOT_FOUND`, unreadable targets are silently omitted from `getMany`.
- **Frontend** `@/features/entity-icons`:
  - `IconPicker` — controlled (`value` / `onChange`), no entity knowledge. `categories` restricts the Lucide categories a screen offers (typed `IconCategoryId`); omit it to offer all. `variant="dialog"` opens a larger picker in a centered modal instead of the default compact popover. `allowColor={false}` hides the swatches and saves every pick with `defaultColor` (palette key, default `orange`), which is also the preselected color when color choice is on.
  - `EntityIconPicker entity={...}` — loads and saves on its own, like `CommentsButton`.
  - `EntityIcon` — `value` (already loaded) or `entity` (loads itself) plus a `fallback` icon component (painted in `fallbackColor`); renders the fallback for no icon or an unknown name.
  - `useEntityIcons(refs)` — one batched query for a list; `iconFor(ref)` returns the value or `null`. `useSetEntityIcon` / `useClearEntityIcon` for forms that save on submit.

## Enabling icons for a new entity type

1. Add an entry to `entityIconTargets` in `packages/api/src/v1/entity-icon/targets.ts` with `readable` and `writable` returning the subset of ids the caller may touch (reuse the feature's own ownership/permission query; one query per batch).
2. In that entity's delete handler, call `deleteEntityIcons({ entityType, entityIds }, tx)` from `#v1/entity-icon/handler`.
3. In the UI, render `<EntityIconPicker entity={{ entityType, entityId }} />` or an `IconPicker` inside the entity's form, and `EntityIcon` wherever the entity is shown (batch lists with `useEntityIcons`).

No schema or migration change is needed. Keep per-screen category choices next to the consumer, in the slice's `model/`.

## Catalog and palette

- The picker's catalog (`picker/model/icon-catalog.generated.json` + `icon-categories.generated.ts`) is generated by `bun run icons:catalog` from Lucide's upstream metadata for the installed `lucide-react` version. The same command first writes `packages/content/src/contract/lucide-icons.generated.ts` (`scripts/generate-icon-names.ts`): every name `DynamicIcon` draws, which is what a content repository's `icono` may be; `tests/unit/lib/lucide-icon-names.test.ts` fails when it no longer matches the installed `lucide-react`. Re-run it after upgrading `lucide-react` and commit the output; never edit it by hand. It is fetched as a static asset only when a picker opens. Category titles and tags stay in English.
- Colors are stored as keys, never raw values. Each key has a flat `--icon-<key>` token (light + dark) in `src/styles/theme.css` and an entry in `picker/model/palette.ts`, which is typed exhaustively against the API's keys, so a new key fails `check-types` until both exist.
