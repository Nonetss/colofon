# Data fetching (TanStack Query over oRPC)

Every server read and write in `apps/frontend` goes through TanStack Query v5, with query options and keys generated by oRPC's TanStack Query utils (`orpc` in `apps/frontend/src/lib/orpc.ts`). One `QueryClient` (`apps/frontend/src/lib/query-client.ts`) is shared by every island in the browser and mounted by `QueryProvider` in each `*-page.tsx`. Persisted islands keep it across View Transitions navigations, so a cache entry left stale on one page is still stale on the next.

## Reads

- **A component reads with TanStack Query's hooks over oRPC's options**: `useQuery(orpc.v1.<feature>.<method>.queryOptions({ input }))`, and for cursor pages `useInfiniteQuery(orpc.v1.<feature>.<method>.infiniteOptions({ input: (cursor) => ({ ...filters, cursor, limit }), initialPageParam: null, getNextPageParam: (lastPage) => lastPage.nextCursor }))`. There is no hydration wrapper: islands are `client:only`, mounted with `createRoot`, so nothing server-rendered has to match the first client render. Never fetch into `useState` from a `useEffect`.
- **Everything the read depends on goes in `input`**, so it is part of the key: filters and the table's sort make each combination its own entry, and an infinite list starts again from page one when they change (`use-users-list.ts`).
- **A custom `queryFn`** (a batch split into chunks of the backend's cap, a debounced search) still takes its key from oRPC (`orpc.….queryKey({ input })`), and each `.call()` inside it passes `{ context: { read: true } }` (`references/api/http-semantics.md`). Examples: `use-comments.ts`, `use-entity-icons.ts`.
- **A read that waits on a value** (a selected id, an open entity) gets `skipToken` as its input until the value exists, from a named helper with an early return (`function branchInput(slug: string, branch: string | null) { if (branch === null) return skipToken; return { slug, branch } }`; for an infinite read the helper returns `skipToken` or the `(cursor) => input` function). oRPC then disables the query by itself. Never key a read with a stand-in id (`"00000000-…"`, `""`) plus `enabled` (`features/admin/git-repository/hooks/use-git-browser.ts`, `useAdminUser`). `enabled` stays for gates that aren't a missing value (`entities.length > 0`, a dialog that is closed).
- **Derive in the query, not in render**: `select` to map or filter the cached data (`surface-search-sources.ts`), `placeholderData: keepPreviousData` when a key changes but the previous result should stay on screen (`useCommentCounts`).
- **Infinite lists load the next page** only when `hasNextPage && !isFetchingNextPage`, through `useInfiniteScroll` and its sentinel.
- **Freshness**: the client default `staleTime` is 60 s; don't override it per query without a reason. Data that changes on the server while a page is open is pushed by a `watch*` stream (below), never polled with `refetchInterval`.
- **Retries** are the client's `shouldRetryQuery` (`lib/query-client.ts`): an error whose status is 4xx (an `ORPCError`'s code mapped through `COMMON_ERROR_STATUS_MAP`, or Better Auth's `status`) surfaces at once, except 408 and 429; anything else is retried up to 3 times. Don't set `retry` per query.
- Several reads whose count is only known at runtime go through one `useQueries` (`use-surface-search-records.ts`), not hooks in a loop.

## Server-rendered content

The documentation reader is the one place that reads in Astro frontmatter: its pages are rendered on the server so the text is in the HTML (`pages/index.astro`, `pages/[repo]/[...path].astro`, and the Markdown routes `pages/llms.txt.ts`, `pages/[repo]/llms.txt.ts` and `pages/[repo]/[...path]/llm.txt.ts`). They read with `createServerClient(Astro.request)` (`lib/orpc-server.ts`, built on `lib/server-link.ts`): an oRPC client that calls the backend at `BACKEND_URL` directly, sends every call as `QUERY` and forwards only the visitor's credentials (`cookie` and `x-api-key`), so the backend sees the session the middleware already checked. It only reads (the backend refuses `QUERY` on a write). An `ORPCError` with `NOT_FOUND` becomes the 404 page (`Astro.rewrite("/404")`). Data a server-rendered page hands to an island goes in as a prop and becomes that query's `initialData` (`DocsSidebar` with `v1.docs.nav`), so the island renders without a request and shares the browser cache from then on. Islands never use the server client.

## Query keys

- **oRPC is the key factory.** `.queryKey({ input })` is the exact key of a plain query and `.infiniteKey(...)` of an infinite one; `.key({ input? })` is a partial prefix that matches both. Invalidate and `setQueriesData` with `.key()` (a partial `input` like `{ jobId }` matches every filtered variant); `getQueryData`/`setQueryData` need the exact `.queryKey()`.
- A slice whose keys other slices invalidate exports them as functions from its hook file (`entityIconsKey`, `commentsListKey`).
- **Hand-written keys are only for reads that don't go through oRPC**: Better Auth's client (`authClient.admin.*`) and `useSearchSuggestions`' `queryKeyPrefix`. They are arrays of JSON-serializable values, entity first, so one prefix reaches every read of that entity, and they come from a key factory, never inline. Admin user reads take theirs from `adminUserKeys` (`lib/admin-user-keys.ts`): by id, by ids, the search and the overview counters, all under `adminUserKeys.all()`, which every admin user mutation (`use-user-mutations.ts`) invalidates. A new Better Auth admin user read adds its key there.

## Writes

- **`useOrpcMutation`** calls the procedure, toasts the outcome and invalidates the given key prefixes once it succeeds. **`useResourceMutation`** adds an optimistic patch of one cached list: cancel its in-flight reads, snapshot, apply `applyOptimistic`, roll back on error, invalidate the list plus `extraInvalidate` on settle. Both wait for their invalidations, so the mutation stays pending until the affected reads have refetched, and a dialog closed on success already shows the new data.
- **Every mutation names what it makes stale**: the list, plus every other read that shows the changed entity (its detail `get`, batched counts or statuses, a parent list whose counts change). Use `.key()` prefixes so plain and infinite variants are both covered.
- **Optimistic patches** are for creates and deletes in a list whose new shape follows from the input (`use-api-keys.ts`); a created row gets a temporary `__optimistic_…` id and is replaced when the invalidation refetches. Anything else just invalidates.
- Toast titles are Spanish; the thrown error's message becomes the description. A caller that reports errors itself (a dialog that stays open) uses `useMutation` directly (`use-entity-icon-mutations.ts`).
- **Server-pushed changes**: a hook opens the procedure's `watch*` stream with `keepConnected` (`lib/event-stream.ts`) inside an effect and invalidates the affected keys on every event, `subscribed` included, since events aren't replayed after a reconnection. No page subscribes to a stream right now (the cron pages that did were removed); `lib/event-stream.ts` and its tests stay for the next one. Never `liveOptions`/`streamedOptions` (`references/api/http-semantics.md`).

## What generic guidance doesn't apply here

- **No React SSR**: islands are `client:only="react"`, so dehydrate/`HydrationBoundary` and route-level prefetching have nothing to hydrate. Data loads in the island, except what a server-rendered page passes as `initialData` (above).
- **No persistence or offline mode** (`persistQueryClient`, `networkMode`).
- **No query error boundaries**: each surface renders the query's `isError` state itself, with `refetch` as the retry.
- Query hooks aren't unit-tested (`references/writing-unit-tests.md`); validate with `check-types` + Biome.
