# Workspaces

Bun workspaces are `apps/*` and `packages/*` (root `package.json`). `bunfig.toml` sets `linker = "isolated"`. `apps/gateway` has no `package.json`, so it is not a workspace.

## Apps

### `apps/frontend`

- Astro 7 SSR (`@astrojs/node` standalone), React 19 islands, Tailwind v4 via Vite plugin, shadcn/ui (`base-nova` style on Base UI, neutral, lucide icons; `components.json`), TanStack Query + oRPC (`src/lib/orpc.ts`).
- Dev `astro dev` on `:4320` (`dev` script, `strictPort`), behind the dev gateway's `https://localhost:4321`. It still proxies `/rpc`, `/api`, `/mcp`, `/scalar`, `/openapi.json` → `BACKEND_URL` (default `http://localhost:3000`) for direct hits, but sign-in only works on the gateway origin. In the Docker dev stack it listens on `0.0.0.0:4320` inside its container (`expose`, never `ports`). In production Docker, Astro alone listens on `0.0.0.0:4321` (compose `expose`, never `ports`) and `apps/gateway` serves it, plus the backend API, on the public port.
- Check `astro check`. Unit tests (`bun test` + happy-dom + Testing Library) in `tests/unit/`, outside `src/`; no end-to-end suite.
- The main surface is the documentation reader: `src/pages/index.astro` (the "Todos" home) and `src/pages/[repo]/[...path].astro` (plus its Markdown routes for AIs: `llms.txt.ts`, `[repo]/llms.txt.ts`, `[repo]/[...path]/llm.txt.ts`), rendered on the server through `src/lib/orpc-server.ts` with the `Docs.astro` layout (`frontend/navigation-and-layouts.md`); `/admin` keeps its own shell.
- Middleware `src/middleware.ts` gates auth; layouts in `src/layouts/`; pages in `src/pages/`; features in `src/features/<domain>/`; providers in `src/providers/`; route identity in `src/lib/app-surfaces.ts`.
- PWA: `public/manifest.webmanifest` and the service worker `public/sw.js`, registered by `src/layouts/service-worker.astro` (included by `Layout.astro` and `Admin.astro`) in production builds only. In dev that component unregisters any worker and deletes its cache, because the worker would intercept every unbundled Vite module.
- `scripts/generate-icon-catalog.ts` regenerates the entity icon picker's Lucide catalog (`bun run icons:catalog`, see `frontend/entity-icons.md`).

### `apps/backend`

- Hono 4 + oRPC on Bun. HTTP only, `:3000` (`Bun.serve` without a `port`, so `PORT` or else 3000).
- Served explicitly with `Bun.serve({ id: "backend", fetch: app.fetch })` — there is no `export default app`.
- Entrypoint `src/index.ts`: `startContentSync()` (logs the content source and starts its first sync without awaiting it), then `seed(auth)` from `@nonete/db/seed` applies migrations and seeds the admin, then `startCron()` (`src/cron/index.ts`) starts the scheduler and syncs code-declared jobs.
- On `SIGINT`/`SIGTERM` it shuts down in order — cron run-event streams → HTTP (5 s drain, then open connections are cut) → cron → database pool — under an 8 s hard timeout.
- `bun --hot` re-executes `src/index.ts` on every change; bootstrap, signal handlers and the server handle are guarded on `globalThis` for that reason. `apps/backend/turbo.json` marks `dev` as interruptible so `turbo watch` can restart it.
- Routers `src/routers/{auth,docs,rpc}.ts` (+ `handler-plugins.ts`), middlewares `src/middlewares/{auth,request-logger,no-store}.ts` (`no-store` marks the content schema endpoints `Cache-Control: no-store`) (request logger first; `sessionMiddleware` skips `/api/auth/*`, where Better Auth resolves the session itself), cron wiring `src/cron/{index,run-as}.ts`. `GET /` returns `OK` for healthchecks.
- Dev `bun run --hot src/index.ts`. Build `tsdown` → `dist/index.mjs`; `deps.alwaysBundle` inlines every dependency because the runtime image ships no `node_modules`. Check `tsc -b`.

### `apps/site`

- The project website, a static Astro 7 build (`output: "static"`, Tailwind v4, no React, no API) published to GitHub Pages at `https://nonetss.github.io/colofon/` by `.github/workflows/pages.yml`. It has nothing to do with the running app: no auth, no backend, no Docker image, and the gateway never serves it. Its `package.json` is still copied by every app Dockerfile, since `bun install --frozen-lockfile` needs all workspace manifests.
- `base: "/colofon"` with `trailingSlash: "always"`; every internal link goes through `href()` / `localized()` in `src/lib/url.ts`. English at the root, Spanish under `/es/` (`src/i18n/ui.ts` holds every landing string for both).
- Landing (`src/components/Landing.astro`: hero, screenshot tour, architecture, install) plus a docs collection, one Markdown file per page and language in `src/content/docs/<lang>/<slug>.md` (frontmatter `title`, `description`, `order`).
- The tour shows captures of the running app reading `doc-example`, in `src/assets/screenshots/` (`src/lib/screens.ts`). Every screen ships as a pair, `<name>.webp` and `<name>-dark.webp` (its `dark` field), 2400×1500; the frame and the lightbox show the one for the site's `.dark` theme. The site opens in the dark theme unless the visitor picked light. The design tokens and faces mirror `apps/frontend/src/styles/theme.css`, and `src/components/Logo.astro` is the app's mark.
- Dev `astro dev --port 4322` (`bun run dev:site`). Check `astro check`.

### `apps/gateway` (not a workspace)

- Docker assets only: `routes.caddy`, `Caddyfile`, `Caddyfile.dev`, `Dockerfile` (`caddy:2-alpine`, copies the three into `/etc/caddy`, runs `Caddyfile`), and a dev `compose.yml` (host network for the native apps, `localhost` upstreams, runs `Caddyfile.dev`) started by `bun run gateway`. `routes.caddy` is the only place that maps requests to apps.
- `routes.caddy`, the site body every site imports (zstd/gzip, security headers): `/health` answers `ok` (the compose healthcheck); `/rpc/*`, `/api/*`, `/git/*`, `/mcp`, `/scalar*`, `/openapi.json` → `BACKEND_HTTP_UPSTREAM` (`backend:3000`), with `/git/*` left uncompressed (git packs); everything else → `FRONTEND_HTTP_UPSTREAM` (`frontend:4321`).
- `Caddyfile` (production): one HTTP site, `:{$GATEWAY_HTTP_PORT:80}` (`h1`/`h2c`, `admin off`, `auto_https off`).
- `Caddyfile.dev` (dev only): one site, `https://localhost:4321` (`tls internal`, `h1`/`h2`), the dev URL and the only port dev exposes; `auto_https disable_redirects`, `skip_install_trust`, and its own local CA name (`pki` → `colofon dev Local Root`/`Intermediate`): Caddy's default name is the same in every project, so a browser trusting another project's CA fails with `SEC_ERROR_BAD_SIGNATURE`. Its CA lives in `/data` (volume `stack-dev_gateway_data`, shared by both dev compose files); `bun run dev:cert` exports the root.
- It is the only service with `ports` in `compose.yml` and `compose.prod.yml`.

`NODE_ENV` defaults to `development`; `production` (set by the compose files and Dockerfiles) switches logging to JSON lines. Logs go to stdout only.

### `packages/content` layout

`src/` holds only `index.ts` (the public barrel, the package's single export) and one folder per area. Areas import each other in one direction only: `contract` imports no other area, `git`, `diagrams` and `styles` import only `contract`, `pages` imports `contract`, `diagrams` and `styles`, and `editor` imports `contract` and `diagrams`. No module imports itself back through others, type-only imports included. `tests/structure.test.ts` reads the real tree and fails on a file outside an area, a forbidden direction or a cycle; the rule itself is the `content-package-structure` spec. A helper two areas need lives in the lowest area both may import from.

- `contract/`: the meta-schema in zod (`meta-schema.ts`: `doc.config.yaml`, each `catalog/<type>/_type.yaml` and the field kinds, under contract 2's English names); the contract versions (`versions.ts`: `contract: "2"`, or `plataforma: "1"` for a contract 1 repository) and the contract 1 reading (`contract-1.ts`: the Spanish names by position, translated to contract 2 before validation, problem paths mapped back, and the editor schemas renamed); `entitySchema()` (`entity-schema.ts`) building an entity's schema from its `_type.yaml`; `loadContent()` (`load.ts`) reading a content root's declarations (`doc.config.yaml`, the optional `menu.yaml`, every `_type.yaml`) with Spanish problems per file, and `parseJson` reading strict JSON with `jsonc-parser`; `readCatalog()` (`catalog.ts`) reading and validating every entity file with its label and page; `iconName` (`icon-name.ts`) checking every `icon` against the Lucide names in `lucide-icons.generated.ts`; the catalog page paths and where an entity links (`catalog-paths.ts`); `PageProblem` (`problems.ts`), the problem pages, diagrams and styles report; `isImageFile` (`images.ts`), the image files a page can show; `RESERVED_SLUGS` (`reserved-slugs.ts`), the slugs a repository can't take, checked against the frontend's pages and the gateway's routes by `tests/contract/reserved-slugs.test.ts`.
- `git/`: the clones (`source.ts`: `cloneFolder()` placing each repository's clone under `.content/<id>/`, `pruneClones()` removing clones of deleted repositories, `createRepoSync()` keeping a clone current with the git CLI, pinned to its folder with `GIT_DIR`/`GIT_WORK_TREE`, credentials redacted, `readEditDates()` giving each file its last commit date); the git server of hosted repositories (`hosting.ts`: `ensureBareRepo()` creating a bare repository under `.hosted/<id>/`, `createGitHttpHandler()` serving git's smart HTTP protocol with `git upload-pack`/`receive-pack --stateless-rpc` as a fetch handler); `readFolder()`/`readFile()` (`browse.ts`) reading a bare repository's folders and files on a branch with `git ls-tree`/`cat-file`, behind the admin `v1.content.readFolder`/`readFile` procedures and the `/admin/git/<slug>` code screen.
- `editor/`: the editor's JSON Schemas and their catalog in SchemaStore's format (`schemas.ts`: `editorSchemas()`, `schemaCatalog()`).
- `diagrams/`: the `<Diagram>` component's files. `read.ts` reads every `diagrams/<id>.json` (or a hand-drawn `diagrams/<id>.svg`, read through a whitelist in `illustration.ts`) and dispatches each file. A file without `type` is in the format of the reference site's scheme drawer `lib.mjs` (`drawn.ts`): the content places every box, arrow and zone, checked against the catalog, the pages and `schema.ts`, its text measured as `lib.mjs` does (`measure.ts`). A file with `type` is one of the typed forms in `types/` (diagram-design's grammars: one module per type, all listed in the single `DIAGRAM_TYPES` array of `types/index.ts`, laying the data out into a `Scene` (`types/kit/scene.ts`) with shared helpers in `types/kit/` and pure layout helpers in `types/layout/`, with its budget, legend and text version). `model.ts` holds the types and `accentPaths` every diagram module shares. `figure.ts` builds the figure, with its caption and its text version kept off screen for screen readers and `llm.txt`, and `svg.ts` draws it as a sanitized inline SVG with `doc-diagram-*` classes and the `data-*` the reader's highlighting reads (tagged boxes and shapes, tables, curves, UML heads, hues, badges, a legend). `report.ts` holds the report and salvage helpers every diagram reader uses.
- `styles/`: a repository's optional `styles/` (`content-styles`). `modules.ts` lists the module names in the platform's order (`theme`, `page`, … `sections`, each restyling one of `apps/frontend/src/styles/`) and the size limits; `clean.ts` parses one module with `css-tree` and keeps only an allow-list (no `@import` or other unlisted at-rule, no resource but `data:` images and fonts or the repository's own `docs/` images rewritten to the reader's route, names decoded before they are compared, every `<` escaped, what css-tree could not parse removed); `read.ts` (`readStyles()`) reads, cleans and joins the modules, reporting unknown entries and oversized modules.
- `pages/`: `readSite()` (`site.ts`) reads every `docs/**/*.mdx` into a validated header (`header.ts`) and a sanitized hast tree (`parse.ts`, `transform.ts`, `to-hast.ts`): GFM, `[!KIND]` alerts, heading ids, links, `catalog:` links and images resolved to reader routes, and the platform's components `<Callout>`, `<Entities>` (`entities.ts`, a catalog table) and `<Diagram>` replaced by their blocks. ESM, expressions, ` ```diagram ` fences and other JSX are reported, never run. It also builds the navigation (`nav.ts`: the folders and the catalog, or the groups of `menu.yaml` with a last "Otros" group; a folder holding only its `index.mdx` is a page, not a section; what the menu says about an entry's title and icon wins over the page header), the generated catalog pages (`catalog-pages.ts`: `catalog`, `catalog/<type>`, `catalog/<type>/<id>` with the pages citing an entity and the entities referencing it, `references.ts`; fields are named by their optional `label`, `fieldLabel()` in `entities.ts`), the reading order, the per-page problems and the repository's stylesheet (`readStyles()`, on `Site.styles`, its problems on the home). The API caches each repository's site per checkout (`v1/content/reader.ts`'s `site()`) and serves it through `v1.docs`. `formerNameProblems()` (`former-names.ts`) reports, as site problems, the former Spanish folders and files (`catalogo/`, `diagramas/`, `estilos/`, `_tipo.yaml`), which are never read, and `contract1Problems()` reports a repository still on contract 1.

## Docs and design

- `README.md` (English) is the human overview; `AGENTS.md` holds the hard rules for agents (`CLAUDE.md` only imports it); `PRODUCT.md` (Spanish) is the product context.
- Spanish guides for humans in `docs/human/`, one file per topic with `README.md` as the reading-order index. Their diagrams and the root README's are `docs/diagrams/*.html` sources exported to `docs/img/*.svg` under the same name.
- `DESIGN.md`, `PRODUCT.md` and `.impeccable/` feed the Impeccable design skill.
- OpenSpec lives in `openspec/`: one spec per capability in `openspec/specs/<capability>/spec.md` (list them with `openspec list --specs`); finished changes are in `openspec/changes/archive/`.

## Content repository

The documentation itself is not in this repo: each site lives in a git repository of its own, either at its root or in a folder of it (the row's `content_path`, e.g. `docs` for a site kept inside a code repository; the reader joins it to the clone folder through `contentRoot`/`resolveContentRoot`; the forms offer the folders holding a `doc.config.yaml` at the chosen ref from `v1.content.listContentFolders`/`listMyContentFolders`, read with a tree-only fetch by `listContentFolders` in `@nonete/content`, and sync, hosting and the git browser still see the whole repository), with `doc.config.yaml`, an optional `menu.yaml` (the sidebar), `docs/` (MDX; `docs/catalog/` is reserved for the generated catalog pages), `catalog/<type>/` (`_type.yaml` + one YAML per entity), an optional `diagrams/`, an optional `styles/` (style modules, applied over the platform's styles on that repository's pages) and `skills/`. The content repositories are rows of `content_repository` (slug, name, git URL with any credentials, ref, content folder, last sync), managed by admins at `/admin/content` through the `v1.content` procedures. A repository is either external (a git URL) or hosted by the platform: a hosted one stores the marker `/git/<slug>.git` as its URL (`packages/api/src/v1/content/hosting.ts` owns it), keeps a bare repository in `.hosted/<id>/` (git-ignored), and is cloned, fetched and pushed with no credentials at `<origin>/git/<slug>.git` (`apps/backend/src/routers/git.ts` mounts the handler); a push syncs it at once. The backend clones each into `.content/<id>/` (git-ignored), a hosted one from its bare repository on disk, and refreshes them on boot, every five minutes (the `v1.content.sync` cron job), when one is created or its URL or ref changes, and on demand. Editors get a repository's YAML schemas from its public catalog `GET /api/v1/content/schemas/<slug>` through one setting, `yaml.schemaStore.url` (`docs/human/contenido.md`); the content repository holds no generated files.

`doc-example/` is a real sample content repository, kept in this repo as a git subtree of `git@github.com:Nonetss/doc-example.git` (`main`) so agents always have one at hand: read it to see what the platform renders, and check content-facing changes (the meta-schema, pages, menus, diagrams) against it. It is not a workspace: Biome (`biome.json`) skips it, and the platform never reads its content from disk; to render it, register it as a content repository at `/admin/content`. It has its own `AGENTS.md`, and `doc-example/.agents/skills/` is the only copy of the `colofon-*` writing skills, which the backend serves as platform skills (`references/api/agent-skills.md`): the Docker context (`.dockerignore`) keeps only that folder of it, and the backend image copies it. Edit its files like any other, commit them in this repo (never mixed with code changes in one commit), and sync with its own repository from the repo root with a clean working tree:

```bash
git subtree pull --prefix=doc-example git@github.com:Nonetss/doc-example.git main --squash  # bring its upstream commits in
git subtree push --prefix=doc-example git@github.com:Nonetss/doc-example.git main           # publish the commits made here
```

Always pass `--squash` on pull, as the subtree was added squashed; never clone it again inside `doc-example/` (no nested `.git`).

## What git tracks (vs `.gitignore`)

- `.env` and `.env*.local` are ignored; `.env.example` is tracked.
- `.vscode/*` is ignored except `settings.json`, `tasks.json`, `launch.json` and `extensions.json`.
- Of the agent folders only `.claude/settings.local.json`, `.claude.lock` and `.agents.lock` are ignored; `.agents/skills/<name>/` holds the skills and `.claude/skills/<name>` symlinks to them (`../../.agents/skills/<name>`).
- `.github/*` is ignored except `.github/workflows/`.
- Drizzle migrations in `packages/db/src/migrations/` use the drizzle-kit ≥ 0.31 folder format (`<timestamp>_<name>/migration.sql` + `snapshot.json`).
