# Cron scheduling

Any oRPC procedure becomes a schedulable job by adding the `cronMeta` plugin (from `#index`) to its `.meta(...)`: `.meta(openapi({...}), cronMeta({ eligible: true }))` — no registry, no extra wiring (`plugins.list` does this). To have the code impose the schedule instead, declare `cronMeta({ schedule: "<UTC cron expression>", name?, description? })` (`name` defaults to the key, `description` to the `openapi()` description or summary; `health.check` declares `schedule: "* * * * *"`); the two forms are mutually exclusive (`CronMeta` in `packages/api/src/index.ts`).

- **Code-declared schedules** (`cron.schedule`): at backend startup `syncDeclaredJobs` (`packages/cron/src/declared.ts`) reconciles them with `cron_job` rows of `source = 'code'` — matches rows by handler key, creates the missing ones, updates a changed expression, name, description or run-as user in place, disables one whose expression is invalid and soft-deletes those no longer declared. They run in UTC with `{}` as input (so the procedure takes no required input) as the seed administrator: `syncCodeDeclaredJobs` (`apps/backend/src/cron/index.ts`) resolves the `ADMIN_EMAIL` user (`apps/backend/src/cron/run-as.ts`) and stores it as the jobs' `user_id`, so protected and admin procedures work and keep their normal authorization. When that user doesn't exist the jobs run with no user and startup logs a warning naming them — only public procedures and `cronProcedure`s work then; a non-admin `ADMIN_EMAIL` account is bound with a warning and never elevated. They are read-only: the service rejects `update`/`setEnabled`/`remove`/`runNow` (`CronReadOnlyError` → `CONFLICT` in `packages/api/src/v1/cron/handler.ts`), and they are absent from `v1.cron.handlers`. Their key is just as stable as an eligible one — renaming the procedure starts a new job and splits its history.

- **Cron-eligible keys are stable.** `cron_job.handler_key` persists the procedure key (its dot path under `v1Router`), so an eligible procedure is never renamed, moved or stripped of eligibility without proposing a data migration to the user.
- `packages/api/src/v1/cron/discovery.ts` walks `v1Router` with `walkProcedureContractsSync` once (lazily cached) and collects every eligible procedure (key, summary/description/tags via `#shared/procedure-docs`, input as JSON Schema) and every declared schedule, reading the meta with `getCronMeta()`; unknown or non-eligible keys resolve to `NOT_FOUND`.
- `packages/api/src/v1/cron/runtime.ts` is a bind-slot: `packages/api` cannot build the cron service itself, so `apps/backend/src/cron/index.ts` builds it with the scheduler (`packages/cron`) and binds it at startup.
- `cron_job` stores the handler key, `source` (`manual` | `code`), UTC cron expression, enabled flag, optional run-as `user_id` and optional JSON payload; `cron_run` records one row per execution attempt.
- The scheduler (`packages/cron`, in-process, `Bun.cron`, UTC only) fires each job by calling the resolved procedure through oRPC's `call()` with a context carrying `cron: { jobId, jobName }` and the job's payload as input. A job bound to a user (`cron_job.user_id`) runs with a real session created by `createUserSession()` (`packages/auth/src/session.ts`) and revoked after the run, so every middleware sees that user as the caller; the cron marking itself grants nothing.
- HTTP contexts never set `context.cron`, so a `cronProcedure` is unreachable over HTTP even by an admin.
- **Single-instance by design**: no distributed lock. Multiple backend replicas run every job once per replica.
- **Run events**: `createScheduler`'s `onRunChange` fires after every `cron_run` write (`running`, `success`/`failed` once the job's `lastRunAt`/`nextRunAt` are updated, `skipped`). It is never awaited, and a listener failure is only logged. The backend wires it to `publishCronRunChange` in `packages/api/src/v1/cron/events.ts`, an in-memory `@orpc/publisher` kept on `globalThis` so `bun --hot` doesn't split it. `v1.cron.watchRuns` (GET, `protectedProcedure`, no cron meta) streams one job's changes over SSE: `subscribed` once listening, then `run` events. Nothing is replayed, so clients refetch on `subscribed`. `v1.cron.watchJobs` (same shape, no input) streams `changed` for anything that may alter the job list: the publisher's `list-changed` event, sent with every run change by `publishCronRunChange` and with every job write by `publishCronJobsChange()`, which the backend calls from the cron service's `onChange` next to the scheduler refresh. In-memory means only subscribers on the replica that ran the job see it, the same single-instance limit. Shutdown ends them through `closeCronEvents()`, registered in `src/v1/lifecycle.ts` and reached from the backend via `closeStreams()` (`@nonete/api/lifecycle`), before the HTTP drain.
- Endpoints (`packages/api/src/v1/cron/router.ts`): `adminProcedure` for mutations (`create`, `update`, `setEnabled`, `remove`, `runNow`), `protectedProcedure` for reads (`list`, `get`, `listRuns`, `handlers`, `watchRuns`, `watchJobs`).
- `remove` is a soft delete (`cron_job.deleted_at`); job-name uniqueness is a partial unique index on `deleted_at is null`, and a second one keeps one active code-declared job per handler key.
- Frontend: none. The `/crons` pages were removed when the frontend became the documentation reader; jobs are read and managed through the `v1.cron` endpoints (`/scalar` lists them for admins), and the content sync shows its outcome per repository in `/admin/content`. The `watchRuns`/`watchJobs` streams and `cron.listRuns`'s filters and sort stay for a future admin screen.
