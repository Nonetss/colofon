Se lanzan con `errors.<CÓDIGO>()` importado de `#errors`, nunca con
`new ORPCError(...)`. El mensaje que ve el usuario va en español; los
internos, en inglés:

```ts
throw errors.NOT_FOUND({ message: "Comentario no encontrado" })
```

El código tiene que decir **cuál es la causa**:

| Código | Cuándo |
| --- | --- |
| `BAD_REQUEST` 400 | La entrada es inválida o incoherente más allá de lo que comprueba zod: un cursor mal formado, una expresión cron inválida, un tipo de entidad que no admite iconos. |
| `UNAUTHORIZED` 401 | No hay nadie autenticado. |
| `FORBIDDEN` 403 | Hay usuario, pero **este** usuario no tiene el rol, el permiso o la propiedad. Otro sí podría. También una API key en un `sessionProcedure`. |
| `NOT_FOUND` 404 | No existe, **o es privado de otra persona**: un repositorio de contenido de otro usuario responde 404. |
| `CONFLICT` 409 | La entrada es válida y el usuario podría, pero el estado o el tipo del objetivo lo impide para todo el mundo: un slug duplicado, un cron declarado en código. |
| `PRECONDITION_FAILED` 412 | Una credencial git guardada ya no se puede descifrar («La credencial guardada no se puede leer: guárdala de nuevo»). |
| `INTERNAL_SERVER_ERROR` 500 | El servidor rompió algo que debería cumplirse siempre (un `insert().returning()` sin fila). |
| `BAD_GATEWAY` 502 | Falla un servicio externo: git no puede traer un repositorio de contenido (`content.syncRepository`) o leer sus ramas o carpetas (`content.listBranches`, `content.listContentFolders` y sus versiones `My`), con el error de git sin credenciales. |
| `SERVICE_UNAVAILABLE` 503 | Algo no está configurado en este servidor: los secretos y las credenciales git sin `SECRETS_ENCRYPTION_KEY`. |

`src/errors.ts` declara todos los códigos estándar de oRPC (de `BAD_REQUEST`
a `GATEWAY_TIMEOUT`) con su mensaje por defecto, pero no su estado HTTP: lo
ponen los manejadores de `/rpc` y `/api`. El cuerpo de un error lleva `code`,
`message` y `data`.

## Dos distinciones que se confunden

- **403 o 404.** Si el usuario ni siquiera debería saber que el recurso
  existe (es privado de otro), responde 404 para no filtrar su existencia:
  filtra por dueño en el `where` y usa `assertFound`. 403 solo cuando lo
  puede ver pero no modificar.
- **403 o 409.** ¿Podría hacerlo un admin o el dueño? Entonces 403. ¿No
  puede nadie, por cómo está el objetivo? Entonces 409. Un 400 nunca es la
  respuesta a una entrada válida que se rechaza por el objetivo.

Los errores de validación de zod ya se convierten solos en `BAD_REQUEST`: no
se vuelve a validar la misma regla a mano.

## Cómo se registran

Los manejadores de oRPC registran cada error de procedimiento una sola vez
(`apps/backend/src/routers/handler-plugins.ts`), con un nivel según la causa:
`warn` para un 4xx, `error` para cualquier 5xx (también `BAD_GATEWAY` y
`SERVICE_UNAVAILABLE`) o una excepción inesperada, e `info` si el cliente
canceló la petición. La línea lleva el mismo `requestId` que el resto de
líneas de la petición.
