El formato lo decide Biome (`bun run check`, o `bun run format` para formatear sin el linter): 2 espacios, comillas dobles, sin punto y coma, 80 columnas y los imports ordenados. Además hay reglas que Biome no comprueba. Todas buscan lo mismo: que lo que el código decide se vea, y que el compilador no deje pasar errores de tipos. Valen para todo fichero TypeScript de `apps/*` y `packages/*`, nuevo o tocado.

## No se permite

| Patrón | Ejemplo |
| --- | --- |
| Casts que silencian al compilador | `valor as Tipo`, `valor as unknown as Tipo`, `valor!` |
| Tipos genéricos o formas inventados para que algo encaje | `TData = unknown` que nadie necesita, `(...args: never[]) => unknown` en un `satisfies` |
| Cadenas de `??` | `a ?? b ?? c ?? null` |
| `??` con un valor por defecto que no es literal | `job.description ?? job.cronExpression` |
| Ternarios anidados o dentro de una expresión | `list.flatMap((x) => (x.ok ? [x.id] : []))`, `return missing ? null : filled` |
| Memoizar con `let` + `??=` | `let spec; const get = () => (spec ??= build())` |

## Sí se permite

- Un `??` con un literal: `user.name ?? ""`.
- Un ternario simple como valor de una asignación: `const mode = enabled ? "on" : "off"`.
- El encadenamiento opcional para leer: `user?.role === "admin"`, mientras no alimente una cadena de `??`.
- Los alias de import (`import { appRouter as v1Router }`), que no son casts.

## Qué hacer en su lugar

- Para un valor que puede ser de otro tipo, **estrecharlo con una comprobación** (`if (typeof x === "boolean") return null`, como en `packages/api/src/shared/procedure-docs.ts`), no con `as`.
- Para una comprobación que se repite después, **convertirla en un *type guard*** (`isDeclaredSchedule` en `packages/api/src/v1/cron/discovery.ts`).
- Para un registro de entradas de tipos distintos, comprobarlo con `satisfies` contra la forma común en vez de borrar su tipo (`surface-search-sources.ts`, en `apps/frontend/src/features/app-shell/authenticated/model/`).
- Para varios valores por defecto, **una función con nombre y `return` tempranos**, comparando con `!== undefined` o `!== null` para conservar el sentido de `??`:

  ```ts
  function jobDescription(job: CronJob): string {
    if (job.description !== null) return job.description
    return job.cronExpression
  }
  ```

- Para filtrar y transformar, `.filter().map()` o un bucle `for`.
- Para objetos que dependen de una condición, dos `return` explícitos.
- Antes de memoizar, comprobar que compensa.

## Si un tipo no encaja

No se fuerza. Se busca el tipo que expone la librería, se estrecha con comprobaciones o se replantea el diseño. Si sigue sin haber una forma limpia, se para y se consulta antes de escribir un cast.

La referencia completa, con los ejemplos reales del código, es `.agents/skills/stack/references/code-style.md`.
