## La cookie

- La sesión es una **cookie** `httpOnly`, `secure` y `SameSite=Lax`, firmada
  con `BETTER_AUTH_SECRET`.
- Better Auth guarda sus datos en una caché de cookie durante 60 segundos,
  para no consultar la base de datos en cada petición.
- Como la cookie es `secure`, sobre `http` plano solo funciona en
  `localhost`. Por eso en desarrollo se entra por el gateway en `https`.

## Los dos clientes del frontend

| Cliente | Dónde corre | A quién llama |
| --- | --- | --- |
| `src/lib/auth-client.ts` | En el navegador | `/api/auth` en el mismo origen |
| `src/lib/auth-server.ts` | En el servidor de Astro | El backend, por `BACKEND_URL` |

Los dos cargan los mismos plugins de cliente (API keys, admin y
organizaciones, con los mismos roles), para que el usuario de la sesión
traiga los mismos campos en los dos lados.

## En el backend

Un middleware de Hono (`apps/backend/src/middlewares/auth.ts`) resuelve la
sesión de cada petición a partir de la cookie o de una cabecera `x-api-key`,
y la deja en el contexto de Hono, de donde la toman oRPC, `/mcp` y el log de
la petición (que registra el id y el email del usuario). Se lo salta en dos
rutas: `/api/auth/*`, donde Better Auth la resuelve por su cuenta, y
`/git/*`, el servidor git de los repositorios alojados, que no usa sesión.

Si llegan cookie y API key a la vez, gana la clave.

## El middleware del frontend

`apps/frontend/src/middleware.ts` se ejecuta antes de cada página y de cada
ruta del servidor de Astro:

1. Deja pasar `/login`, `/signup` (y sus subrutas) y `/logo.svg` sin sesión.
2. Pregunta la sesión al backend con las cabeceras de la petición, así que
   una API key en `x-api-key` también vale.
3. Si no puede consultarla (el backend está caído), responde
   `503 Service Unavailable` y lo registra como `auth_service_error`. Una API
   key rechazada (`401` o `403`) no cuenta como caída: se trata como alguien
   sin sesión.
4. Si no hay sesión:
   - `/llms.txt` y el descubrimiento de skills (`/.well-known/agent-skills/`)
     responden igualmente, con solo lo que no necesita clave;
   - los `llm.txt` de las páginas y los `/<slug>/llms.txt` responden `401`
     con una línea que explica cómo enviar una API key y apunta a
     `/llms.txt`;
   - todo lo demás redirige a `/login`.
5. Si alguien sin rol `admin` entra en `/admin`, lo redirige a `/`.
6. Reenvía al navegador las cookies de sesión renovadas.

## Qué falla

| Síntoma | Causa | Qué hacer |
| --- | --- | --- |
| Toda página responde `Service Unavailable` | El frontend no llega al backend | Revisa que el backend esté arrancado y `BACKEND_URL` |
| Vuelves a `/login` después de iniciar sesión | La cookie no se guarda: entras por `http` fuera de `localhost`, o no entras por el origen del gateway | Entra por la URL de `CORS_ORIGIN` |
| Un agente recibe `401` en un `llm.txt` | No envía la API key, o la clave caducó o se borró | Crea otra en `/me/api-keys` ([API keys](api-keys.mdx)) |
